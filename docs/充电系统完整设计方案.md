# 充电系统完整设计方案（用户端 · 管理端 · 后端 · 数据库）

> 适用项目：东软电动汽车充电桩应用管理平台（ChargingPlatform，Qt5/Qt6 + SQLite，双程序：ChargingServer / ChargingClient）
> 定位：在现有「选桩 → 建单 → 模拟 → 结算」最小闭环之上，设计一套**状态机完整、并发安全、可断线恢复、四端闭环**的充电系统。
> 配套文件：`database/upgrade_charging_v2.sql`（数据库迁移，可直接执行）、`docs/充电系统设计可视化.html`（架构/状态机/时序/ER 图）、本文档。

---

## 0. 设计目标与范围

### 0.1 要解决的核心问题（现状诊断）

现有充电链路（`client/pages/ChargingPage.cpp` → `server/network/ClientHandler.cpp` → `dao/OrderDao.cpp`）已跑通最小闭环，但存在 8 个结构性短板：

| # | 短板 | 现状（已读代码确认） | 后果 |
|---|------|---------------------|------|
| 1 | 订单只有 2 态 | `types.h`：`OrderCharging=0 / OrderFinished=1` | 无排队、预约、取消、异常概念 |
| 2 | 无预授权/余额冻结 | `processStartCharge` 不校验余额；`processStopCharge` 结算时才查余额 | 充到一半余额不足被拒，桩被白白占用 |
| 3 | 无并发原子保护 | 先 `PileDao::getById` 查状态，再 `OrderDao::create` + `setStatus`，两步非原子 | 两个请求并发可同时通过检查，同一桩被建两单 |
| 4 | 模拟绑定连接线程 | `ClientHandler` 私有 QTimer；断线即 `stopProgressTimer` | 客户端断线 → 订单永久卡在"充电中"，桩永久占用；服务端重启后所有未完成订单无人推进 |
| 5 | 无费率规则 | 单价固定 `station.price`（元/度） | 无峰谷分时、无服务费、无计费快照 |
| 6 | 无充电目标 | 充电只能手动结束 | 不能"充到 X 度/充 X 元/充 X 分钟"自动结束 |
| 7 | 无订单管理 | 管理端 5 个页面均无订单管理 | 无法远程结束、退款、查历史 |
| 8 | 无异常处理 | 桩故障时在用订单无处置路径 | 故障即死锁 |

### 0.2 设计原则

1. **兼容优先**：保留现有字段语义（`status 0=充电中 1=已完成` 不变），只做增量扩展；旧演示数据可继续使用。
2. **引擎与连接解耦**：充电模拟从 `ClientHandler` 私有定时器迁到服务端全局 `ChargingEngine`，断线/重启均可恢复。
3. **原子抢占**：所有"抢桩/抢单"操作统一走 `UPDATE ... WHERE status=0` 原子判定 + 事务。
4. **演示友好**：沿用"3 秒真实时间 = 1 分钟模拟充电"的节奏，全部参数集中可配。
5. **四端闭环**：用户端（发起/排队/结算/历史）— 管理端（监控/费率/强制结束/退款）— 后端（状态机/引擎/计费）— 数据库（订单/费率/排队/流水）各司其职。

## 1. 总体架构

### 1.1 组件与数据流（与现有代码结构对应）

```
┌─────────────────────┐        TCP 长连接 JSON        ┌──────────────────────────────────────────┐
│  ChargingClient     │  ──────────────────────────▶  │  ChargingServer（同一进程，两个角色）      │

│  · 充电页            │   请求/应答 + 推送             │  ├─ TCP 服务端（ClientHandler 每连接一线程）│
│  · 排队页            │                               │  ├─ ChargingEngine（新增，全局充电引擎）    │
│  · 订单历史页        │                               │  └─ HttpServer（Web 大屏，只读）           │
└─────────────────────┘                               └──────────────────┬───────────────────────┘
                                                                         │  QSQLITE（WAL）
                                                                ┌────────▼────────┐
                                                                │ SQLite test.db  │
                                                                │ admin/user/     │
                                                                │ station/pile/   │
                                                                │ charge_order/   │
                                                                │ price_rule(新)  │
                                                                │ reservation(新) │
                                                                │ recharge_log(新)│
                                                                └─────────────────┘
```

- **用户端**：不直连数据库，全部业务经 TCP 协议交互（保持现有约束）。
- **管理端**：与服务端同进程，直接读库/调 DAO/调引擎接口（远程结束、退款、费率配置都是本地调用，不新增管理协议）。
- **后端**：`ClientHandler` 只做"请求校验 + 事务写库 + 应答"，不再持有充电模拟定时器；所有"进行中的充电"由全局 `ChargingEngine` 统一推进。
- **数据库**：仍是唯一持有者 = 服务端；SQLite WAL 模式支持多线程并发读写（已开启）。

## 2. 订单状态机设计（核心）

### 2.1 状态定义（向后兼容扩展）

```cpp
// types.h 新增（保留 0/1 原语义）
enum OrderStatus {
    OrderCharging   = 0,   // 充电中（原值不变）
    OrderFinished   = 1,   // 已完成（原值不变）
    OrderWaiting    = 2,   // 排队中（已登记排队/预约，未上桩）
    OrderCancelled  = 3,   // 已取消（用户取消 / 排队超时释放）
    OrderAbnormal   = 4,   // 异常中断（充电中桩故障 / 引擎异常兜底）
};

// 结束原因（charge_order.finish_type）
enum FinishType {
    FinishByUser      = 0,  // 用户手动结束
    FinishByTarget    = 1,  // 达到充电目标自动结束
    FinishByBalance   = 2,  // 余额耗尽自动结束
    FinishByTimeout   = 3,  // 排队超时释放（订单不产生，见 reservation）
    FinishByAdmin     = 4,  // 管理员强制结束
    FinishByFault     = 5,  // 桩故障中断
};

// 充电目标类型（charge_order.target_type）
enum TargetType {
    TargetNone    = 0,  // 不限，直到手动结束
    TargetEnergy  = 1,  // 按电量（度）
    TargetAmount  = 2,  // 按金额（元）
    TargetMinutes = 3,  // 按时长（分钟）
};
```

### 2.2 状态迁移表（合法迁移 + 触发条件）

| 当前状态 | 迁移到 | 触发事件 | 关键动作（谁来做） |
|---------|--------|---------|-------------------|
| （无单） | OrderWaiting | 用户对"在用"桩发起排队 | ClientHandler 插入 reservation；**不建 charge_order**（排队实体独立于订单，见 4.3） |
| （无单） | OrderCharging | 用户对"空闲"桩发起充电 | 冻结余额 → 原子抢占桩 → 建单（status=0） |
| OrderWaiting | OrderCharging | 引擎分配：桩释放 → 队首用户收到推送 → 用户确认开始 | Engine 置 reservation 已分配；用户确认后走"开始充电"流程 |
| OrderWaiting | OrderCancelled | 用户取消排队 / 分配后 30s 未确认 | ClientHandler / Engine 定时器 |
| OrderCharging | OrderFinished | 用户手动结束 | 事务结算：解冻+实扣 → 完成订单 → 释放桩 → 引擎检查队列 |
| OrderCharging | OrderFinished | 达到目标（电量/金额/时长） | Engine 自动结算（finish_type=1） |
| OrderCharging | OrderFinished | 余额耗尽（amount ≥ balance） | Engine 自动结算（finish_type=2） |
| OrderCharging | OrderFinished | 管理员强制结束 | 管理端调 Engine::forceFinish（finish_type=4） |
| OrderCharging | OrderAbnormal | 桩被置故障 | Engine 心跳检测 → 订单置异常 → 推送事件；管理端可退款转 Finished |
| OrderAbnormal | OrderFinished | 管理员退款/归档 | 管理端 OrderManagePage 处理（记 refund_amount） |

> 说明：为控制复杂度，**排队使用独立实体 `charge_reservation`，不占 charge_order 状态**；OrderWaiting 仍保留，供将来把"排队单"并入订单表时使用。状态机图中两者都画出。

## 3. 数据库设计

### 3.1 新增表（共 3 张）+ 订单表扩展

#### 3.1.1 `price_rule` 分时费率表（新增）

```sql
CREATE TABLE IF NOT EXISTS price_rule (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    station_id  INTEGER NOT NULL,            -- 所属充电站
    period      INTEGER NOT NULL DEFAULT 0,  -- 时段：0=低谷 1=平段 2=高峰
    start_time  TEXT NOT NULL DEFAULT '00:00', -- 时段起点 HH:MM
    end_time    TEXT NOT NULL DEFAULT '24:00', -- 时段终点 HH:MM
    price       REAL NOT NULL DEFAULT 1.0,   -- 电价（元/度）
    service_fee REAL NOT NULL DEFAULT 0.0,   -- 服务费（元/度，可选）
    FOREIGN KEY(station_id) REFERENCES station(id)
);
```

- 每站 3 条（峰/平/谷），启动迁移时按 `station.price` 自动生成默认档位；`period` 的默认时段建议：峰 10:00-12:00 & 17:00-21:00、谷 23:00-07:00、平 其余。计费按 `start_time <= 当前时刻 < end_time` 命中的记录，未命中回退 `station.price`。
- **计费快照**：订单开始充电时，把命中费率写入订单的 `price_snapshot`，充电期间改费率不影响进行中订单。

#### 3.1.2 `charge_reservation` 排队 / 预约表（新增，一张表两种业务）

> 设计取舍：排队（人在现场等空闲桩）与预约（提前锁定某个桩的某个时段）放在同一张表，用 `type` 区分——两者共享"占用/取消/过期"的状态语义，DAO 与页面可复用，也便于管理端统一管理。预约的核心是**时段冲突校验**：同一桩同一时段最多一个有效预约。

```sql
CREATE TABLE IF NOT EXISTS charge_reservation (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id       INTEGER NOT NULL,
    pile_id       INTEGER NOT NULL,
    station_id    INTEGER NOT NULL,
    type          INTEGER NOT NULL DEFAULT 0, -- 0=排队(现场等) 1=预约(提前锁定时段)
    create_time   TEXT DEFAULT (datetime('now','localtime')),
    -- 排队业务字段
    assign_time   TEXT,                       -- 引擎分配（轮到）时间
    expire_time   TEXT,                       -- 分配后确认截止时间
    -- 预约业务字段
    reserve_date  TEXT,                       -- 预约日期 yyyy-MM-dd
    reserve_start TEXT,                       -- 预约开始时刻 HH:MM
    reserve_end   TEXT,                       -- 预约结束时刻 HH:MM
    status        INTEGER DEFAULT 0,          -- 0=有效(排队中/预约待履约) 1=已分配/已到桩
                                              -- 2=已取消 3=已过期 4=已履约(转订单)
    FOREIGN KEY(user_id) REFERENCES user(id),
    FOREIGN KEY(pile_id) REFERENCES pile(id),
    FOREIGN KEY(station_id) REFERENCES station(id)
);
```

- **排队**（type=0）：一个用户同时最多 1 条 status=0/1 的记录（服务端校验）。引擎在桩释放时：取该桩 `status=0` 最早一条 → 置 1（已分配）+ 写 assign_time/expire_time → 推送 `PushOrderEvent(轮到你了)`；30 秒（真实秒，可配）内未确认开始 → 置 3（过期）→ 继续分配下一位。
- **预约**（type=1）：用户选择"日期 + 时段（默认 30 分钟粒度）"提交 → 服务端做时段冲突校验 → 通过则插入 status=0（待履约），占用该时段；到预约开始时间前 10 分钟推送 `PushOrderEvent(预约提醒)`；用户到桩后点"开始充电" → 置 4（已履约）并转入正常订单流程；超过预约结束时间 15 分钟未到桩 → 置 3（已过期），时段释放。

### 3.3 并发与事务策略（重要）

SQLite 单写者，多线程下用 **`BEGIN IMMEDIATE` 事务** + **原子条件 UPDATE** 保证不重不漏：

```sql
-- 抢桩（ChargingEngine::acquirePile，替代现有"查-写"两步）
BEGIN IMMEDIATE;
UPDATE pile SET status = 1 WHERE id = :pid AND status = 0;  -- 影响行数==1 才算抢到
-- 抢到才继续：INSERT charge_order ... / UPDATE user 冻结余额
COMMIT;
```

- 冻结余额与抢桩放在**同一事务**：余额不足直接回滚，桩保持空闲。
- 结算同理：解冻 + 实扣 + 完成订单 + 释放桩，一个 `BEGIN IMMEDIATE ... COMMIT`。
- WAL + busy_timeout=3000 已在 `DatabaseManager::init` 开启，多线程读不受影响。

## 4. 后端设计（ChargingEngine + 协议 + 处理链）

### 4.1 ChargingEngine（新增，核心改造）

**职责**：所有"进行中的充电"的统一推进器，与客户端连接完全解耦。

- 单例，独立工作线程（或主线程 QTimer，二选一，推荐独立线程避免与 UI 竞争）。
- 心跳周期：**3 秒**（沿用现模拟节奏：3s 真实 = 1 分钟模拟充电），参数集中：
  - `kTickMs = 3000`、`kMinutesPerTick = 1`（= 现 ClientHandler 常量，迁移至此）。
- 启动流程（服务端 `main.cpp` 在数据库初始化后启动引擎）：
  1. 扫描 `charge_order WHERE status = 0` → 全部注册进引擎内存表（服务重启自动恢复）。
  2. 扫描 `pile WHERE status = 1` 且有对应 charging 订单的桩保持占用；孤儿占用（无订单的 status=1）自动释放回空闲。
- 每个心跳，对每个注册订单：
  1. `energy += power * kMinutesPerTick / 60.0`（kWh）
  2. `amount = energy * price_snapshot`（含服务费）
  3. 写库 `UPDATE charge_order SET energy=?, amount=? WHERE id=? AND status=0`
  4. 检查终止条件（任一命中即自动结算）：
     - `target_type=1 && energy >= target_value` → 结束（finish_type=1）
     - `target_type=2 && amount >= target_value` → 结束（finish_type=1）
     - `target_type=3 && 模拟分钟 >= target_value` → 结束（finish_type=1）
     - `amount >= 用户当前余额` → 结束（finish_type=2，防透支）
     - `桩状态 == PileFault` → 订单置 OrderAbnormal（finish_type=5），推送异常事件
  5. 向订单所属用户推送 `PushOrderProgress`（若该用户在线）。
- 结算动作统一走 `settleOrder(orderId, finishType, reason)`，与手动结束共用同一事务函数（见 4.3）。
- 队列扫描：每次结算释放桩后，调用 `ReservationDao::next(pileId)` 分配队首并推送事件。

**接口**：

```cpp
class ChargingEngine : public QObject {
    Q_OBJECT
public:
    static ChargingEngine &instance();
    bool start(QString *err);                       // 扫描恢复 + 启动心跳
    bool registerOrder(int orderId);                // 新订单注册（StartCharge 成功后调用）
    bool settleOrder(int orderId, int finishType,   // 统一结算（手动/自动/管理端共用）
                     const QString &reason, QString *err);
    bool forceFinish(int orderId, const QString &reason, QString *err);  // 管理端
    int  queueSize(int pileId);                     // 排队人数（列表页展示）
signals:
    void orderFinished(int orderId, int finishType); // 供管理端页面刷新
};
```

```cpp
ReqReservePile    = 12,  // {userId, pileId, action}  action: 0=排队 1=取消排队

ReqOrderHistory   = 13,  // {userId, page?, pageSize?} → {orders:[...], total}
ReqOrderDetail    = 14,  // {userId, orderId} → {order}
ReqStationFee     = 15,  // {stationId} → {rules:[{period,startTime,endTime,price,serviceFee}], defaultPrice}
ReqAppointPile    = 16,  // {userId, pileId, reserveDate, reserveStart, reserveEnd} → 提交预约
                         //   成功: {reservationId, message}；失败: ErrSlotConflict / ErrSlotPast
ReqMyReservations = 17,  // {userId} → {reservations:[{id,pileCode,stationName,type,status,
                         //   reserveDate,reserveStart,reserveEnd,queuePos,createTime}]}
ReqAppointSlots   = 18,  // {pileId, date} → {slots:["08:00-08:30","08:30-09:00",...],
                         //   booked:[{"start":"08:30","end":"09:00"}]}  已占用时段(含进行中订单占用的当前时段)
// 服务端推送（新增）
PushOrderEvent    = 102, // {orderId?, reservationId?, event, message, queuePos?}
                        //   event: 1=轮到你了(排队,请确认开始) 2=订单已结束(自动) 3=订单异常中断
                        //          4=排队位置变化 5=充电已开始 6=预约提醒(到预约时段了)
                        //          7=预约成功/已取消
```

> 兼容策略：`ReqStartCharge(9)` 保留原语义（不带目标 = 不限目标，默认冻结金额），新客户端用 `ReqStartChargeExt(11)`；两套入口服务端同一处理函数，避免旧二进制不兼容。

### 4.3 服务端处理链（ClientHandler 改造）

**ReqStartChargeExt（新主流程）**：
1. 校验用户存在、未冻结、无进行中订单（status=0/2）。
2. 校验桩存在、空闲。
3. 计算目标与冻结额：
   - `TargetNone`：冻结 = `min(50, balance)`（固定兜底 50，不足按余额，余额 < 10 拒绝）
   - `TargetEnergy`：冻结 = `targetValue × 当前单价 × 1.2`（上浮容差）
   - `TargetAmount`：冻结 = `targetValue`
   - `TargetMinutes`：冻结 = `功率kW × 分钟/60 × 单价 × 1.2`
4. `BEGIN IMMEDIATE`：查余额 → 余额 ≥ 冻结额？→ `UPDATE pile SET status=1 WHERE id=? AND status=0`（原子）→ 插入订单（含 target/price_snapshot/freeze_amount）→ 扣减冻结（`balance -= freeze`）→ `COMMIT`。
5. 引擎注册订单，返回 `{order, freezeAmount, price}`。
6. 推送 `PushOrderEvent(event=5 充电已开始)`。

**ReqStopCharge（改造）**：校验归属与状态 → 调用 `ChargingEngine::settleOrder`（事务：解冻 + 实扣 + 完成 + 释放桩 + 队列分配）→ 返回 `{order, balance}`。

**ReqReservePile**：校验桩在用、无重复排队、队未满 → 插入 reservation(status=0) → 返回排队位置（`COUNT(*) WHERE pile_id=? AND status=0 AND id < 本记录` + 1）。

**取消排队**：`UPDATE charge_reservation SET status=2 WHERE id=? AND user_id=? AND status=0`。

**ReqAppointPile（预约提交，新）**：
1. 校验桩存在、`station/pile.allow_reserve=1`、用户无重复预约（同一桩 status=0/1 记录最多 1 条）。
2. 时段合法性：`reserveStart < reserveEnd`；`reserveDate + reserveStart` 晚于当前时间（否则 ErrSlotPast）。
3. 冲突校验（同一桩同一时段只能一个有效预约，与插入同一事务）：
   ```sql
   BEGIN IMMEDIATE;
   SELECT COUNT(*) FROM charge_reservation
    WHERE pile_id = :pid AND type = 1 AND status IN (0,1)
      AND reserve_date = :date AND reserve_start < :end AND reserve_end > :start;
   -- 命中>0 → 回滚返回 ErrSlotConflict
   INSERT INTO charge_reservation (user_id, pile_id, station_id, type, reserve_date,
                                   reserve_start, reserve_end, status)
   VALUES (:u, :pid, :sid, 1, :date, :start, :end, 0);
   COMMIT;
   ```
4. 返回 `{reservationId}`，推送 `PushOrderEvent(event=7 预约成功)`。
5. 引擎预约定时任务：开始前 10 分钟推送 event=6 提醒；超过预约结束 +15 分钟未履约 → status=3 过期释放时段。

**ReqAppointSlots（可约时段查询）**：返回该桩该日全部 30 分钟粒度时段 + 已占用列表（含进行中订单占用的当前时段、status=0/1 的预约时段），客户端直接置灰。

**断线语义变化（重要）**：客户端断开**不再**影响充电——引擎继续推进、自动结束、队列分配照常；用户重连后 `ReqUnfinishedOrder` 返回进行中/异常订单，客户端恢复对应视图。

### 4.4 计费模型

```
实付金额 amount = 累计电量 energy × price_snapshot
price_snapshot = 命中的时段电价 + 服务费（订单开始时定格）
冻结/解冻：
  开始：balance -= freeze_amount（冻结额进订单）
  结算：balance += freeze_amount（解冻）→ balance -= amount（实扣）
  即净效果：balance -= (amount - 0)，等价 balance = balance_after_freeze + freeze - amount
```

边界：若 `amount > freeze_amount`（异常超耗，正常流程不会发生），差额从剩余余额补扣；余额仍不足则按可扣部分结算并记录 `cancel_reason='余额不足，部分结算'`。

## 7. 完整充电时序流程（8 个场景）

> 图中标注的均为协议消息/数据库事务；完整图见 `充电系统设计可视化.html`，此处为文字化分步说明。

### 场景 1：正常充电全链路（核心主流程）

```
用户端              服务端 ClientHandler            ChargingEngine              数据库
  │                        │                             │                        │
  │── ReqStationPiles ────▶│                             │                        │
  │                        │── 查询桩列表 ────────────────────────────────────────▶│
  │◀── {piles} ────────────│                             │                        │
  │── ReqStartChargeExt ──▶│   {pileId,targetType,target}│                        │
  │   {target=30元}        │                             │                        │
  │                        │── BEGIN IMMEDIATE 事务 ─────────────────────────────▶│
  │                        │   1) 校验余额≥冻结额                                 │
  │                        │   2) 原子抢占桩 status=0→1                           │
  │                        │   3) 插订单(status=0,冻结30,快照1.45)                │
  │                        │   4) 扣冻结 balance-=30                              │
  │                        │── COMMIT ───────────────────────────────────────────▶│
  │                        │── 引擎注册订单 ────────▶│                            │
  │◀── {ok,order,freeze} ──│                             │                        │
  │                        │                             │── 每3秒tick ──────────▶│
  │                        │                             │   energy+=p*1/60       │
  │                        │                             │   amount=energy*1.45   │
  │◀── Push101 进度 ───────┼──────── 引擎广播进度 ────────│                        │
  │  (energy/amount/目标)  │                             │                        │
  │  ......（循环）.........│                             │                        │
  │── ReqStopCharge ──────▶│                             │                        │
  │   {orderId}            │── settleOrder(事务) ───────▶│── BEGIN ─────────────▶│
  │                        │   解冻+30 实扣-amount       │   完成订单(status=1)   │
  │                        │   释放桩 status=1→0         │   写 finish_type       │
  │                        │   检查队列→分配队首          │── COMMIT ─────────────▶│
  │◀── {ok,order,balance} ─│◀── 结算结果 ────────────────│                        │
  │                        │                             │── 通知队首用户(若有) ─▶│
  │◀── Push102 轮到你了 ────┼─────── 队列用户（场景2）─────│                        │
```

### 场景 2：排队 → 自动分配

1. 用户 B 见桩在用 → `ReqReservePile{pileId, action:0}` → 服务端插入 reservation(status=0)，返回 `queuePos=2`。
2. 用户 A 结束充电 → 引擎 settleOrder 释放桩 → `ReservationDao::next(pileId)` 取队首（B 前面的用户）→ 置 status=1 + assign_time/expire_time（now+30s）→ 推送 `PushOrderEvent(event=1)` 给该用户。
3. 该用户确认 → 走场景 1 的 StartChargeExt。
4. B 收到 `PushOrderEvent(event=4 queuePos=1)`（位置前移通知，可选）。
5. 若被分配用户 30s 未确认 → 置 status=3（过期）→ 自动分配下一位。

### 场景 3：达到目标自动结束

1. 用户设置 targetType=2 targetValue=30。
2. 引擎 tick 检测 `amount >= 30` → 调 settleOrder(finish_type=1) → 事务结算 + 释放桩 + 队列分配。
3. 推送 `PushOrderEvent(event=2, message="已达充电目标(30元)，订单已自动结算")` + `Push101 最终进度`。
4. 用户端弹出结算结果（与手动结束同一结算单 UI）。

### 场景 4：余额不足（两种路径）

- **开始时不足**：StartChargeExt 事务内冻结失败 → `ErrFreezeNotEnough` → 用户端提示 + 跳转充值，桩保持空闲。
- **充电中耗尽**：引擎 tick 检测 `amount >= balance`（已冻结部分不再计入）→ 自动 settleOrder(finish_type=2) → 推送事件，用户端提示"余额已耗尽，充电自动结束，请及时充值"。

### 场景 5：桩故障中断

1. 管理端将桩置故障（PileStatusPage/管理页）→ `pile.status=2`。
2. 引擎下一 tick 检测到该桩订单 → 订单置 `OrderAbnormal`（finish_type=5，cancel_reason='桩故障'）→ 解冻并按已充量实扣（或按配置：故障单全额退款，演示建议按实扣 + 可退）。
3. 推送 `PushOrderEvent(event=3 异常中断)`。
4. 管理端 OrderManagePage 对该单"退款" → `refund_amount` + 余额回补 + op_log → 状态转 Finished。

### 场景 6：断线 / 服务重启恢复

- **客户端断线**：引擎无感，继续推进（与现实现的关键差异）。
- **服务端重启**：引擎 start() 扫描 `status=0` 订单全部恢复注册；孤儿占用桩（status=1 无订单）自动释放；客户端重连后 ReqUnfinishedOrder 恢复视图。

### 场景 7：管理端远程结束

1. 管理端 OrderManagePage 点"强制结束" → 二次确认。
2. `ChargingEngine::forceFinish(orderId, reason)` → settleOrder(finish_type=4, cancel_reason=reason) → 事务结算 + 释放桩。
3. 推送 `PushOrderEvent(event=2, message="管理员已结束订单")` → 用户端结算单。

### 场景 8：申请预约 → 履约充电（新增）

```
用户端                 ClientHandler              ChargingEngine                数据库
  │                          │                          │                        │
  │── ReqAppointSlots ──────▶│  {pileId, date}          │                        │
  │                          │── 查询该桩该日已占时段 ────────────────────────────▶│
  │◀── {slots, booked} ──────│                          │                        │
  │── ReqAppointPile ───────▶│  {pileId, date, 14:00-14:30}                      │
  │                          │── 时段冲突校验(COUNT, 见4.3) ─────────────────────▶│
  │                          │── INSERT reservation(type=1,status=0) ───────────▶│
  │◀── {reservationId, ok} ──│                          │                        │
  │◀── Push102 event=7 ──────┼─────────────────────────▶│                        │
  │    (预约成功)             │                          │                        │
  │                          │                          │── 定时任务(引擎)：      │
  │                          │                          │   开始前10分钟          │
  │◀── Push102 event=6 ──────┼────── 预约提醒 ───────────│   超过结束+15min未到    │
  │    (该到桩了)             │                          │   → status=3 过期释放   │
  │── ReqStartChargeExt ────▶│  {pileId, ...}           │                        │
  │   (到桩履约)              │── 同场景1(冻结+抢桩+建单) │                        │
  │                          │── UPDATE reservation SET status=4(已履约) ───────▶│
  │◀── {ok, order} ──────────│                          │                        │
  │  ……进入正常充电……         │                          │                        │
```

关键规则：预约只"锁时段"不"锁桩"（桩仍可被现场用户立即充电）；到桩履约时若桩被占（极端情况），优先提示稍等或转排队；冲突校验与插入在同一事务内，保证并发不重复。
