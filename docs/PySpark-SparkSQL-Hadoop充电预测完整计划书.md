# PySpark、SparkSQL 与 Hadoop 充电预测完整计划书

> 版本：V1.0  
> 规划日期：2026-09-12  
> 数据范围：北京模拟充电数据集，2025-01-01 至 2026-09-11  
> 实施边界：新增大数据处理、模型训练和 Web 大屏能力，不修改现有 Qt 客户端、管理端、TCP 协议及 SQLite 核心业务流程。

## 1. 项目结论与总体路线

本项目采用“PySpark 数据治理 → SparkSQL 主题分析 → Spark MLlib 模型训练 → HDFS 结果沉淀 → ECharts 大屏展示”的完整链路。

这里所说的“使用 Hadoop 训练”，准确实现方式是：

- HDFS 负责存放原始数据、清洗数据、特征、模型和预测结果；
- YARN 负责给多个站点训练任务分配 CPU、内存和执行容器；
- PySpark 负责数据检查、清洗和特征工程；
- SparkSQL 负责统计分析与 ADS 指标生产；
- Spark MLlib 负责 GBT、随机森林和 ALS 等模型训练；
- 模型通过 `spark-submit --master yarn` 在 Hadoop 集群上运行，而不是由 HDFS 本身执行算法。

第一阶段以“小时粒度、47 个站点、未来 1/6/24 小时负荷序列”为核心交付；第二阶段完成“用户下一充电时段与电量预测”；最终把真实计算结果接入现有 Web 大屏，并保留静态 JSON 降级能力，保证演示稳定。

```text
北京数据集 ZIP
      │
      ▼
HDFS ODS 原始层（只追加、不改写）
      │
      ▼
PySpark Schema 校验、质量扫描、清洗、隔离
      │
      ▼
HDFS/Hive DWD 明细层（Parquet + Snappy）
      │
      ├───────────────┐
      ▼               ▼
SparkSQL DWS/ADS   PySpark 特征工程
      │               │
      │               ▼
      │       Spark MLlib on YARN
      │       47 站负荷模型 + ALS
      │               │
      └───────┬───────┘
              ▼
     HDFS 预测结果 / 模型注册表
              │
              ▼
      JSON 导出或只读查询 API
              │
              ▼
     现有 ECharts Web 大屏
```

## 2. 建设目标、范围与优先级

### 2.1 建设目标

1. 用 PySpark 自动发现并量化缺失、重复、越界、主外键、时间连续性和业务一致性问题。
2. 建立可重复执行、可审计的清洗流程，原始值、清洗值和异常原因同时保留。
3. 用 SparkSQL 生产运营总览、站点排行、负荷曲线、设备状态、用户画像等大屏指标。
4. 在 Hadoop YARN 上完成多站点负荷预测训练，输出未来 1、6、24 小时序列。
5. 用 Spark ALS 完成用户充电时段偏好和下一次充电量预测。
6. Web 大屏只消费 ADS 结果，不在浏览器中扫描明细数据或临时“编造”模型指标。

### 2.2 实施优先级

| 优先级 | 内容 | 完成标志 |
| --- | --- | --- |
| P0 | HDFS、PySpark 质量检查、清洗、SparkSQL 分析 | 全量 5 张表可重复处理，质量报告可查看 |
| P0 | 47 站小时负荷预测 | 每站输出未来 24 点，可切换查看 1/6/24 小时 |
| P0 | 运营总览与 AI 预测大屏 | 展示真实 ADS 数据、模型指标和数据时间 |
| P1 | 用户下一时段与电量 ALS 预测 | 完成离线评估、冷启动回退和大屏热力图 |

| P2 | 15 分钟预测、置信区间、What-if 模拟 | P0/P1 稳定后实施 |

- 不修改 Qt 客户端和管理端业务页面；
- 不把 700 MB 左右的本地 SQLite 数据库提交到 Git；

## 3. 数据资产盘点与初步质量结论

### 3.1 数据规模

| 数据表 | 实际行数 | 主要用途 |
| --- | ---: | --- |
| `beijing_stations.csv` | 47 | 站点维度、设备数、类型、行政区 |
| `beijing_weather.csv` | 619 | 日期、天气、温度、降水、节假日 |
| `beijing_sessions.csv` | 572,539 | 用户会话、充电量、费用、起止时间 |
| `beijing_snapshots.csv` | 2,792,928 | 47 站 × 619 天 × 96 个 15 分钟点 |
| `beijing_bms.csv` | 2,290,411 | SOC、电压、电流、温度等会话时序 |
| 合计 | 5,656,544 | 模拟数据，固定随机种子可复现 |

### 3.2 已完成的只读初检结果

| 检查项 | 结果 | 处理决定 |
| --- | --- | --- |
| 会话主键重复 | 0 | 继续保留唯一性断言 |
| 会话负电量、负费用、结束早于开始 | 均为 0 | 作为硬规则持续检查 |
| 会话与站点、天气主外键缺失 | 均为 0 | DWD 关联失败时进入隔离区 |
| 天气日期连续性 | 619 天完整，无缺日 | 可直接作为每日外生特征 |
| 快照时间完整性 | 每站每天均为 96 点，无重复 | 可作为设备时序和辅助特征 |
| 快照容量冲突 | 3,319 条，均多出 1 台 | 原值保留；状态统计使用修正字段 |
| `cum_kwh_day` | 2,792,928 行全部为 0 | 判定为无信息字段，不作为负荷标签 |
| 跨午夜会话 | 42,112 条，占 7.355% | 必须按真实时间交集跨日分摊电量 |
| 会话总电量与快照功率积分 | 1,660.69 万 kWh 对 3,925.46 万 kWh，差 136.38% | 两者不是同口径；训练主标签以会话结算电量为准 |
| BMS 主外键、SOC 范围、时序单调性 | 未发现异常 | 保留业务规则校验 |
| BMS 充电电流 | 全部为负 | 是充电方向约定，不按脏数据删除；另派生绝对值 |
| `available_energy (kw)` | 生成逻辑实际表示能量 | DWD 改名为 `available_energy_kwh`，原字段保留 |

### 3.3 预测标签口径决策

站点负荷的主标签采用会话结算电量 `kwhTotal`，按会话与 15 分钟窗口的真实重叠时长进行分摊：

\[
e_{i,j}=kWh_i\times\frac{overlapHours(i,j)}{durationHours_i}
\]

\[
load_{s,j}=\sum_{i\in station_s} e_{i,j}
\]

该方法有三个优点：总电量守恒、跨午夜会话不会丢失、口径与订单结算一致。小时负荷由同一小时内 4 个 15 分钟窗口求和得到。

快照功率积分 `charging_power_kw × 0.25h` 作为“遥测估算负荷”保留，用于设备监控、辅助特征和口径差异告警，不与结算电量强行合并为一个标签。

## 4. Hadoop 与 Spark 环境设计

### 4.1 推荐部署

课程项目优先使用 3 节点环境：1 个 NameNode/ResourceManager，2 个 DataNode/NodeManager；个人开发可先用单机伪分布式验证。开发、测试和答辩环境使用同一套脚本和配置变量。

| 组件 | 作用 | 最低要求 |
| --- | --- | --- |
| HDFS | 原始、清洗、特征、模型、结果存储 | 开启副本和 Web UI |
| YARN | 训练任务资源调度 | 可查看 Application 日志 |
| Spark/PySpark | ETL、SQL、MLlib | 与 Hadoop/Java 版本匹配 |
| Hive Metastore | 表结构和分区管理 | 本地 Derby 仅限单人；小组建议 MySQL/PostgreSQL |
| Python | PySpark 作业入口 | 各节点环境一致 |

具体版本在部署时统一锁定到 `bigdata/conf/versions.env`，不要让组员各自安装不同的大版本。

### 4.2 协作方式

Git 中提交数据集 ZIP、Schema、PySpark/SparkSQL 脚本和启动说明；不提交数据库文件、HDFS 数据块、Spark 临时目录和模型缓存。每位成员首次拉取后运行同一个初始化脚本，将 ZIP 解压并上传到自己的本地或小组 Hadoop 集群。

数据集内 README 的“HDFS 已导入”只表示建议目标路径，不能代替实际集群验收。初始化脚本必须执行 `hdfs dfs -test -e`、行数核对和文件校验和记录。

## 6. 阶段一：PySpark 数据质量检查

### 6.1 检查维度

1. 完整性：空值、空字符串、必需字段、日期覆盖。
2. 唯一性：会话 ID、站点 ID、天气日期、站点-快照时间、会话-BMS 时间。
3. 有效性：数值范围、枚举值、时间格式、星期独热编码。
4. 一致性：主外键、站点类型/行政区一致、状态数量与设备总数一致。
5. 时序性：15 分钟连续性、会话先后顺序、BMS SOC 趋势、跨午夜处理。
6. 分布性：极端值、分位数、站点样本偏斜、用户冷启动规模。
7. 口径性：结算电量与遥测积分差异、字段单位与命名是否一致。

### 6.2 规则分级

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| BLOCKER | 无法进入后续计算，如 Schema 缺列、主键大面积重复 | 停止任务 |
| ERROR | 单行不可用，如结束时间早于开始、外键不存在 | 进入隔离表 |
| WARN | 可修复或口径有风险，如容量冲突、异常分位点 | 修正并保留标记 |
| INFO | 业务约定，如充电电流为负、模拟数据日期 | 记录但不删除 |

### 6.3 质量报告表

统一输出 `ads_data_quality_report`：

| 字段 | 说明 |
| --- | --- |
| `run_id` | 本次流水线唯一编号 |
| `table_name`、`column_name` | 数据表与字段 |
| `rule_id`、`rule_description` | 规则编号与说明 |
| `severity` | BLOCKER/ERROR/WARN/INFO |
| `total_count`、`failed_count`、`failed_rate` | 统计结果 |
| `sample_keys` | 最多 20 个样例主键，不保存敏感明细 |
| `action` | reject/fix/keep/alert |
| `detected_at` | 检测时间 |

PySpark 只做一次 DataFrame 聚合尽量同时计算多条规则，避免每个规则都重新扫描 2,000 万级字段。大表缓存仅在重复使用且集群内存允许时启用。

## 7. 阶段二：数据清洗与标准化

### 7.1 通用规则

- Spark 会话时区固定为 `Asia/Shanghai`；所有文本时间转为 `timestamp`。
- 业务日期由北京时间生成，字段统一为小写下划线。
- 金额、电量使用明确精度的 Decimal，模型特征再转 Double。
- ODS 永不覆盖；DWD 增加 `source_file`、`run_id`、`quality_flags`、`processed_at`。
- 所有写入采用按分区覆盖或幂等 MERGE 设计，重复执行同一批次不产生重复数据。
- 用户 ID 在对外 ADS 和大屏中哈希或匿名化。

### 7.2 各表清洗规则

**站点表**

- `facility_type` 只允许 1=办公、2=商圈、3=住宅、4=高速/景区；
- `device_count > 0`；站点 ID 唯一；
- 当前数据无经纬度，Web 地图使用程序已有导航地图。47 站先按行政区聚合；若要逐站精确落点，后续增加独立坐标维表，不能伪造为精确地址坐标。

**天气表**

- 每日一行，日期连续；`weekday` 与日期重新计算结果一致；
- `holiday` 只允许 0/1，`condition` 只允许 0—4；
- 日最高温不得小于最低温，降水量不得为负；
- 小时模型将日特征广播连接至该日 24 个小时。

**会话表**

- 主键去重、站点/天气关联、时间顺序、时长差异、星期独热编码均校验；
- 42,112 条跨午夜会话不截断，按窗口重叠秒数分配到两天；
- 平均功率 `kwh_total / charge_time_hrs` 仅做异常检测，使用站内分位数/IQR 标记，不直接粗暴删除快充样本；
- 分摊后必须验证每个会话的窗口电量之和等于原 `kwh_total`。

**快照表**

- 保留 `in_use_raw`、`idle_raw`、`fault_raw`；
- 对 3,319 条“满占用且同时故障”的冲突记录，`fault_alarm_raw` 仍用于告警；设备状态计数按下式修正：

\[
faultClean=\min(faultRaw,\max(deviceCount-inUse,0))
\]

\[
idleClean=deviceCount-inUse-faultClean
\]

- `cum_kwh_day` 恒为 0，不插值、不用于训练，仅在质量报告中标记；
- `charging_power_kw × 0.25` 形成遥测估算电量，但不得代替主标签；
- 15 分钟断点使用完整时间网格检测。真实业务接入后，短缺口可标记并插值，长缺口不可插值。

**BMS 表**

- `esd` 重命名为语义明确的 `session_id`；
- 原负电流保留，新增 `charge_current_abs_a = abs(charge_current_a)`；
- `available_energy_kw` 原值保留，清洗字段更名为 `available_energy_kwh`；
- 检查 SOC 0—100、最大值不小于最小值、时间位于会话区间内；
- BMS 暂不进入 P0 负荷标签，可用于后续充电时长、过温风险等亮点。

### 7.3 隔离与回放

ERROR 记录写入 `/charging/dwd/quarantine/`，包含规则编号和原始主键；修复规则调整后可以仅重跑受影响分区。大屏数据质量页显示异常数量，但不展示完整用户明细。

### 8.4 SparkSQL 性能策略

- 47 行站点表和 619 行天气表使用广播连接；
- 会话按 `dt` 分区，站点小时特征按 `station_id, event_hour` 排序；
- 统一先聚合后关联，避免 BMS 直接与全量快照做笛卡尔式连接；
- 开启 AQE，根据集群规模设置 shuffle 分区；
- 写出前控制 Parquet 文件数量，避免数万个小文件；
- 每张 ADS 表保留 `data_time`、`generated_at`、`run_id` 和 `data_nature=模拟数据`。

## 9. 问题一：站点充电负荷预测

### 9.1 任务定义

P0 统一采用小时粒度。对站点 `s`，以时刻 `T` 之前可获得的负荷和外生变量预测未来 24 个小时：

\[
\hat{Y}_s=\{\hat{x}_{s,T+1},\ldots,\hat{x}_{s,T+24}\}
\]

大屏的“1 小时、6 小时、24 小时”分别显示该预测序列的前 1、前 6、前 24 个点。训练主损失选择 MSE，离线验收以 MAE 为主，并同时报告 RMSE、WMAPE、sMAPE 和 R²。存在零负荷时不使用普通 MAPE 作为唯一指标。

### 9.2 特征设计

| 类别 | 特征 |
| --- | --- |
| 时间 | 小时、星期、是否周末、月份、节假日、小时/星期 sin-cos 周期编码 |
| 天气 | 最高/最低/平均温度、天气类型、降水量 |
| 站点 | 站点 ID、站点类型、行政区、设备数 |
| 历史负荷 | lag 1/2/3/6/12/24/48/168 小时 |
| 滚动统计 | 前 6/24/168 小时均值、标准差、最大值、趋势斜率 |
| 设备状态 | 仅使用预测时刻之前的在用率、故障率、排队量及其滞后值 |
| 业务 | 历史订单数、用户数、平均会话电量的滞后值 |

所有滚动窗口必须截止到 `T`，标签通过 `lead` 或预测窗口生成，严禁把未来快照、未来订单数或未来真实天气观测泄漏给模型。未来天气在离线评估中可使用已知天气，在上线演示中必须标注为“天气预报/模拟外生变量”。

### 9.3 数据切分

禁止随机切分时序数据。建议固定为：

- 特征预热：2025-01-01 至 2025-01-07，仅生成 lag/rolling；
- 训练集：2025-01-08 至 2026-05-31；
- 验证集：2026-06-01 至 2026-07-31；
- 测试集：2026-08-01 至 2026-09-10；
- 2026-09-11：作为答辩演示预测起点或最终回放日。

最终一天之后没有完整真实标签，评估样本必须自动删除 label 为空的末端窗口。除固定切分外，再做 3 个时间滚动窗口回测，检查模型是否只在一个月份有效。

### 9.4 基线与模型路线

必须先完成四个可解释基线：上一小时、昨天同小时、上周同小时、过去 8 周同星期同小时均值。

正式路线为：

1. 全局 GBT：47 站合并训练，站点 ID/类型作为特征，用作冷启动和失败回退；
2. 分站 GBT：每个站点训练一个“一步预测”模型，共 47 个模型；
3. 用一步模型递归滚动 24 次，生成完整 24 小时曲线；
4. P1 可增加直接预测第 6/24 小时的校准模型，修正递归累积误差；
5. RandomForestRegressor 与线性回归只作为对比，不为“模型越多越好”而堆叠。

选择 GBT 的原因是数据规模适中、非线性和特征交互明显，并且可在 Spark MLlib/YARN 内完成。Spark 原生 GBT 回归优化平方误差，因此报告中应写“以 MSE 训练、以 MAE 等指标评价”，不能声称其直接优化 MAE。

### 9.5 多站点 Hadoop 训练方式

单站只有约 1.5 万小时样本，不适合为每个站点启动过大的集群。计划将 47 站分成 6 个批次，每批 7—8 站：

```text
submit_load_batches.sh
  ├── YARN Application 1：站点 1001—1008
  ├── YARN Application 2：站点 1009—1016
  ├── ...
  └── YARN Application 6：剩余站点
```

每个 Application 内依次拟合本批站点模型，多个 Application 由 YARN 并发调度。初始资源建议每任务 2 个 executor、每 executor 2 core、2—4 GB 内存，再以 Spark UI 的 GC、shuffle 和执行时间调整；不要一次提交 47 个高资源任务压垮集群。

模型存储示例：

```text
/charging/models/load/station_id=1001/version=20260912_001/model/
/charging/models/load/station_id=1001/version=20260912_001/metrics.json
/charging/models/load/station_id=1001/version=20260912_001/manifest.json
```

`manifest.json` 记录特征版本、数据时间范围、代码提交号、参数、指标、训练时间和是否发布。只有通过验证门槛的版本进入 `production` 指针。

### 9.6 模型选择与回退

- 分站模型验证 MAE 优于全局模型和最佳朴素基线时发布；
- 分站模型退化时使用全局模型；
- 全局模型也未胜过基线时，大屏诚实显示最佳基线，并把该站列入“模型待优化”；
- 不删除表现不好的站点，不用训练集指标冒充测试集指标；
- 对残差按站点和预测步长统计 P10/P90，形成经验预测区间。

### 9.7 派生任务计算

先按站点估计平均单桩有效功率：

\[
\bar{P}_s=median\left(\frac{chargingPower}{inUse}\right),\quad inUse>0
\]

对小时粒度预测，预计占用桩数、空闲桩数和排队数为：

\[
\widehat{busy}_{s,t}=\left\lceil\frac{\hat{x}_{s,t}}{\bar{P}_s\times1h}\right\rceil
\]

\[
\widehat{idle}_{s,t}=\max(0,deviceCount_s-\widehat{busy}_{s,t})
\]

\[
\widehat{queue}_{s,t}=\max(0,\widehat{busy}_{s,t}-deviceCount_s)
\]

峰值预警条件：预测负荷超过站点理论小时容量的 85%，或预计排队数大于 0。15 分钟版本实施时，公式中的 `1h` 改为 `0.25h`，不能直接把 kWh 除以 kW 而忽略窗口长度。

## 10. 问题二：用户充电需求预测

### 10.1 矩阵定义

仅使用 24 个小时会丢失工作日/周末差异，因此采用一周 168 个小时槽：

\[
slot=weekday\times24+hour,\quad slot\in[0,167]
\]

拆成两个矩阵完成两个目标：

1. 时段偏好矩阵 `R_time[u, slot] = log(1 + 该用户在该时段的充电次数)`；
2. 电量矩阵 `R_energy[u, slot] = 该用户在该时段的平均 kWh`。

### 10.2 ALS 训练

- 时段预测：Spark ALS 开启 `implicitPrefs=True`，输出未来候选时段的偏好分；
- 电量预测：使用显式 ALS 拟合平均电量；
- 用户 ID 和时段通过稳定索引映射，索引映射表随模型一同保存；
- 预测下次时间时，在未来 7 天候选中匹配得分最高且尚未过去的 slot；
- 在选中的 slot 上预测 `next_kwh`，并裁剪到训练集中合理分位数范围。

### 10.3 时间切分与指标

对每个用户按时间排序，最后一次会话作为测试，倒数第二次作为验证，其余作为训练，不能随机打散同一用户的未来行为。

| 目标 | 指标 | 基线 |
| --- | --- | --- |
| 下一充电时段 | HitRate@1、HitRate@3、MRR、NDCG@3 | 全局热门时段、用户历史最常用时段 |
| 下一充电量 | MAE、RMSE、WMAPE | 用户历史均值、时段均值 |
| 服务能力 | 覆盖率、冷启动人数 | 不适用 |

离线评估的 `coldStartStrategy=drop` 只用于去除 ALS 无法评分的未知索引；生产输出不能直接丢用户，必须按“用户均值 → 同时段均值 → 全局均值”的顺序回退。对新用户，大屏只展示群体时段分布，不伪装成个性化预测。

### 10.4 隐私与展示边界

Web 大屏展示群体热力图、需求趋势和匿名用户分群，不公开用户 ID、具体行程和单个用户的完整历史。若需要演示单用户预测，使用固定的匿名测试账号。

## 11. 预测流水线与调度

### 11.1 全量首跑


## 14. 测试与验收标准

### 14.1 数据验收

- ODS 实际行数与源文件一致，总计 5,656,544 行；
- 47 个站点、619 个天气日、2,000 个用户均可追溯；

- 质量规则失败不会被简单删除而不留日志。

### 14.2 模型验收

- 47 个站均产出 24 个未来小时点，无缺站、缺步长和负预测值；

## 17. 关键风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 数据为模拟生成 | 泛化能力不能代表真实北京运营 | 全程标注模拟；答辩强调方法验证而非商业准确率 |
| 两种负荷口径差 136.38% | 标签选择错误、预测失真 | 结算电量为主标签，遥测积分单独监控 |
| 跨午夜会话生成快照偏差 | 夜间负荷被低估 | 从会话重新跨日分摊，不依赖原快照累计量 |
| 47 个模型调度开销 | YARN 队列拥堵 | 6 个批次、资源上限、失败重试和全局回退 |
| 随机切分造成高分 | 时间泄漏 | 固定时间切分、滚动回测、自动化测试 |
| 零负荷导致 MAPE 失真 | 指标不可解释 | MAE 主指标，辅以 WMAPE/sMAPE |
| ALS 对新用户无结果 | 大屏缺数 | 用户均值、时段均值、全局均值三级回退 |
| 地图无精确经纬度 | 站点点位不可信 | 先做行政区聚合；后续补坐标维表 |
| 组员环境不一致 | 脚本在他人电脑失败 | 版本清单、统一初始化脚本、最小样本冒烟测试 |

## 19. 完成定义（Definition of Done）

本项目只有同时满足以下条件才算完成：

- 新成员拉取代码后，能按文档将数据上传 HDFS 并跑通样本流水线；
- 全量质量问题可复现、可追溯、可重跑，而不是人工修改 CSV；
- SparkSQL 结果与抽样手算一致；
- 47 个站点均有未来 1/6/24 小时结果及真实离线指标；
- 用户预测有严格时间留出评估和冷启动结果；
- 大屏展示的每个数字都能追溯到 ADS 表、计算口径和 `run_id`；
- Hadoop/模型暂时不可用时，大屏能明确降级且不崩溃；
- 答辩时能现场讲清“Hadoop 负责什么、Spark 负责什么、模型为何可信、数据有哪些局限”。
